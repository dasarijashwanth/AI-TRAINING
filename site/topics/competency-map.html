Competency Map

Reading a section is not the same as being able to do the thing. For each of the six learning sections below, here are the concrete skills you should walk away with, plus one small project that proves you actually have them. If you can do every item on a list, you own that section. If not, you know exactly what to go back and practice.

1. AI Concepts

After this section you can:

  • Explain in plain language what an LLM is doing when it generates text, and why it sometimes hallucinates.
  • Describe what tokens are and estimate how long your inputs and outputs are in tokens.
  • Explain what a context window is and why stuffing too much into it degrades quality.
  • Describe how temperature changes model output and when to turn it up or down.
  • Explain what embeddings are and how they let a model search by meaning instead of keywords.

How to prove it: explain tokens, context windows, and temperature to a friend with zero AI background in under five minutes, using a real example from your own work.

2. AI Safety

After this section you can:

  • List the main ways AI systems fail in practice: hallucinations, data leaks, prompt injection, and biased or harmful output.
  • Decide what data is safe to paste into an AI tool and what must never leave your machine.
  • Write a short safety checklist for any AI workflow you set up.
  • Spot a prompt injection attempt in a document or webpage an agent will read.
  • Explain to a teammate why you review agent output before acting on it, with a concrete example of what can go wrong.

How to prove it: audit one AI workflow you already use (or a sample one), write down its top three risks, and add one safeguard for each.

3. Using AI Agents

After this section you can:

  • Write a prompt that gives the agent a clear role, task, and output format instead of a vague one-liner.
  • Break a big task into a sequence of agent-sized steps with checkpoints you verify yourself.
  • Review agent output critically and catch the confident-sounding mistakes.
  • Set up a small repeatable workflow, like a weekly report or inbox triage, that an agent runs for you.
  • Know when to do the task yourself because the stakes or ambiguity are too high for an agent.

How to prove it: automate one real recurring task from your job end to end, and use it for two weeks straight.

4. Coding with AI Agents

After this section you can:

  • Get a working first draft of a feature from an agent, then shape it into production-quality code yourself.
  • Use an agent to debug a failing test or error by giving it the error output and the relevant code.
  • Ask an agent to review your code for bugs, edge cases, and readability before you open a pull request.
  • Generate unit tests for your code and judge which of the generated tests are actually worth keeping.
  • Refactor legacy code with an agent while keeping behavior identical, verified by tests.
  • Explain what the agent-generated code does line by line, because you never ship code you do not understand.

How to prove it: build a small CLI tool or script with an agent's help, write the tests yourself, and get it running for a real user (even if that user is you).

5. Customizing Agents

After this section you can:

  • Write a system prompt that gives an agent a consistent personality, rules, and scope.
  • Connect an agent to your own documents or data so it answers from your knowledge, not just its training data.
  • Give an agent a tool (like web search or a calculator) and describe exactly when it should use it.
  • Set guardrails so the agent refuses or escalates the tasks it should not handle.
  • Iterate on a custom agent using real examples: try, measure, adjust, repeat.

How to prove it: build a custom agent for one real audience (your team, your community, your customers) and have three real people try it and give feedback.

6. Building Agents

After this section you can:

  • Design a multi-step agent system: which steps exist, what data flows between them, and where a human checks in.
  • Build a working agent with tools, memory, and error handling, not just a chat wrapper.
  • Write an eval suite with real examples and use it to decide whether a change actually improved things.
  • Measure cost per task and pick models using evidence, not hype.
  • Deploy an agent so other people can use it, with logging and a way to see what it did.
  • Handle the failure modes: retries, timeouts, fallbacks, and graceful degradation when the model misbehaves.

How to prove it: ship a deployed agent with a documented eval score and a known cost per task, then present it to someone who was not involved in building it.
