Customizing Agents

Out of the box, an AI agent is a smart generalist. Customizing it turns it into your specialist. This page is about teaching an agent how your project works: standing instructions, reusable skills, your own tools, safe permission boundaries, and memory that survives across sessions. Small effort, big payoff. Customize once, benefit every single day.

Project instructions: AGENTS.md

Every project has unwritten rules. Which package manager, which style guide, where tests live, what you never do. Without those rules written down, the agent guesses. Sometimes it guesses wrong, and you pay for the mistake in tokens and cleanup. A project instructions file fixes this: one markdown file at the repo root, named AGENTS.md, that every coding agent loads automatically when it starts working in your project.

Keep it short and opinionated. List the commands that matter: how to install, how to run tests, how to lint. State the conventions: commit style, branch naming, where docs go. And state the hard no-gos: never edit generated files, never push without tests passing. Ten to forty lines is the sweet spot. If it gets longer, split details into linked files.

Example

Your repo's AGENTS.md reads: "Python 3.12. Install with pip install -e .[dev]. Run pytest before every commit. Format with ruff. Put new utilities in app/utils/, never at the repo root. Never commit .env files." Now every agent session in this repo follows your workflow from the first message, with no reminding needed.

Load it, point at it, or cut it

Instructions only help if the agent actually sees them. Most agents load AGENTS.md automatically, but there are three patterns worth knowing. Load it: the agent reads the whole file into context at session start. Simple, reliable, costs tokens every session. Point at it: your instructions say "see docs/deploy.md for the release process" and the agent reads that file only when the topic comes up. Cheaper, but the agent must notice the pointer. Cut it: split a giant instructions file into smaller topic files so each session loads only what is relevant. This is the best pattern for large projects.

The practical rule: if a rule applies to almost every task, keep it in the root file so it loads. If it applies only to releases, database migrations, or other rare tasks, put it in a linked file the agent opens on demand.

Example

Your root AGENTS.md is 25 lines of daily rules. At the bottom it says: "Releases: read docs/release.md. Database: read docs/db.md." An agent doing a bugfix never pays for the release process. An agent cutting a release loads the full procedure when it needs it. Everyone wins.

Instruction, skill or tool?

When you want the agent to do something new, you have three options, and picking the right one matters. An instruction is a rule in plain language: "always run the tests before committing." Cheap, always on, perfect for conventions. A skill is a packaged how-to: a folder with a description of when to use it and the steps or scripts to follow. Reach for skills when a task repeats and has real steps. A tool is actual software the agent can call, like a code search API or a database client. Tools give the agent new capabilities, not just new knowledge.

Simple test: if you can write it in one sentence, it is an instruction. If it needs steps, files, or example output, make it a skill. If the agent needs to touch a system it cannot reach with its built-in abilities, build or connect a tool.

Example

You want consistent release notes. "Follow the keep-a-changelog format" is an instruction. A skill named release-notes with the format spec, example entries, and a script that drafts notes from git history handles the repeated multi-step work. If the notes must be posted to your internal wiki, a wiki API tool gives the agent the posting ability it lacked.

Writing your first skill

A skill is just a folder with a SKILL.md file inside. The SKILL.md has a name, a description of when the agent should use it, and the instructions: steps, commands, examples. That is the whole format. Do not overthink it. The best first skill automates something you already do by hand at least weekly, something boring and well-defined.

Write it like you are training a smart intern. Start with the trigger: "Use this when..." Then the steps, in order. Include one complete example of input and expected output. Include the common mistakes and how to avoid them. Then stop. A first skill that works for the simple case beats an ambitious skill you never finish.

Example

You write a weekly-summary skill. Its SKILL.md says: "Use when the user asks for a weekly summary. Steps: 1) list merged PRs this week with git log --since='1 week ago', 2) group them by feature vs fix, 3) write a 5-bullet summary in plainspoken voice. Example output included below. Never invent PRs that do not exist." Next Friday, the agent runs it flawlessly.

Who invokes a skill, and where it lives

Skills can be invoked three ways. The user names it: "run the weekly-summary skill." The agent picks it up on its own because the skill description matches the current task. Or a hook fires it automatically at a certain event, like before a commit. The description line is what makes agent-initiated invocation work, so write it like a search query for the task: "weekly summary of merged pull requests" beats "a helpful utility."

Where the skill lives decides who can use it. Project skills live in the repo, travel with the code, and work for everyone on the team. Personal skills live in your agent's config directory and follow you across projects. Team skills live in a shared directory everyone points their agent at. Rule of thumb: if the skill knows project-specific facts, it belongs in the project. If it knows your personal habits, keep it personal.

Example

Your release-notes skill lives in the repo under .agents/skills/release-notes/ because it references your changelog format. Your weekly-summary skill lives in your personal config because it reflects how you like summaries written. A teammate clones the repo and instantly gets the release-notes skill. Your personal habits stay yours.

Testing a skill from a fresh session

A skill that only works in your head is not a skill yet. The test that matters: open a brand new agent session, give it the task with no extra hints, and see if the skill does its job. A fresh session has none of your context, which is exactly what your teammates and future self will have. If the skill depends on something you typed in the same conversation, that dependency is a bug in the skill.

Run the test three times with slightly different phrasings of the request. If the agent picks up the skill each time and produces good output, it is solid. If it misses the skill, the description line needs better trigger words. If the output is wrong, the steps need tightening. Write the failing case down, fix the skill, test again.

Example

You test weekly-summary in a fresh session by typing "summarize this week's merged PRs." The agent never invokes the skill. The description says "weekly summary" but not "merged pull requests." You add those words to the description, test again with "what PRs merged this week?", and this time the agent finds the skill and runs it correctly. Two minutes of testing saved weeks of missed invocations.

Loading only what the skill needs

Every token in context costs money and attention. A skill that loads a 500-line reference file for a 20-line task is burning your budget. The fix is progressive disclosure: the SKILL.md stays short, with the core steps inline, and heavy details live in linked files the agent opens only when needed. Think of SKILL.md as the table of contents, not the textbook.

A good structure: 50 to 100 lines in SKILL.md covering the common path, plus files like reference.md for edge cases and examples.md for worked examples. The agent reads the short version always and the long version only when the task demands it. Your token bill drops, and the agent stays focused instead of drowning in detail.

Example

Your release-notes skill's SKILL.md is 60 lines: the format and the three steps. The gnarly edge cases, like how to handle reverted commits or co-authored PRs, live in edge-cases.md. Routine releases cost the agent 60 lines of context. The one messy release per quarter loads the edge cases when they actually appear.

Reading a plugin before you install it

Plugins and published skills are code written by strangers that your agent will run with your permissions. Install one blind and you have handed a stranger the keys to your machine. Before installing, read the whole thing. Skills are small, so this takes minutes. Look for three things: what it does (the described behavior), what it actually does (every command and file it touches), and what it could do (network calls, credential access, anything outside its stated purpose).

Red flags: a skill that downloads and runs scripts from the internet, one that asks for tokens it does not need, instructions telling the agent to hide what it is doing, or vague "helper" scripts with no comments. A trustworthy skill is boring: clear steps, commented scripts, no surprises. When in doubt, install it in a sandbox project first and watch what it touches.

Example

You find a popular db-migrate skill. Reading its files, you see the migration script also phones home to a stats server with your hostname. The feature works fine, but you do not want telemetry leaking from your machine. You fork the skill, delete the telemetry line, and install your cleaned copy instead. Five minutes of reading saved an ongoing data leak.

Adopting a published skill set

Nobody writes everything from scratch. Published skill sets cover common needs: code review checklists, git workflows, documentation generators, deployment runbooks. Adopting one beats writing your own, because the community has already found the edge cases you have not hit yet. The trick is not adoption, though. It is adaptation: take the published skill, run it on your real tasks, and trim or extend it until it fits your workflow.

The adoption loop: install, try on a real task, note what annoyed you, adjust the skill, repeat. After two or three real runs, it is yours. Keep a small note in the skill about what you changed and why, so future you remembers. And if the upstream skill updates, review the diff like code before pulling it in. Updates can change behavior your workflow depends on.

Example

You adopt a published pr-review skill. On your first real review, it flags style nits your team does not care about and misses your rule that every PR needs a migration rollback plan. You edit the checklist: remove the style section, add the rollback requirement. Third review on, the skill feels native to your team. That is adoption done right.

Connecting an agent to your systems with MCP

MCP, the Model Context Protocol, is how agents talk to outside systems in a standard way. Instead of every agent having a custom integration for every tool, an MCP server exposes tools with a common interface: a name, a description, and typed inputs. The agent discovers what is available, reads the descriptions, and calls tools as the task needs them. Your databases, issue trackers, wikis, and internal APIs all become callable tools for the agent.

Think of MCP servers like USB ports for AI. Your agent is the laptop, each server is a device you plug in. A Postgres server gives the agent safe query ability. A Jira server gives it ticket access. You add and remove connections without changing the agent itself. That separation is the whole point: your data stays in your systems, and the agent reaches it through a controlled, inspectable channel.

Example

You connect a docs server that exposes search_docs and read_doc. Next time you ask the agent "how do we handle refunds?", it searches your internal wiki and answers from your actual policy instead of guessing. You never pasted a single doc into chat. The knowledge stays in your wiki, and the agent reaches through the MCP connection to find it.

Connecting your first tool server

Start with one server and one tool. Pick something read-only and low risk, like a docs search or a read-only database view. The setup is the same almost everywhere: install the server package, add a config entry with the command to launch it and any credentials, then restart the agent so it discovers the new tools. Do not start with your production database. Start with something where a mistake costs you nothing.

After connecting, verify immediately. Ask the agent to list its available tools and confirm the new ones show up. Then run one safe call and check the result. If the tool does not appear, the usual suspects are: wrong command path in the config, a missing environment variable, or the agent needing a restart to pick up the change.

Example

You add a config entry that launches a SQLite docs server: "command": "docs-mcp-server", "args": ["--db", "./docs.db"]. You restart the agent and ask "what tools do you have?" It lists search_docs and read_doc. You ask it to search for "onboarding" and it returns your actual wiki results. Your first MCP connection works, and it took ten minutes.

Logging from a stdio server

Many MCP servers talk to the agent over stdio, meaning they run as a subprocess and chat through standard input and output. That is simple and fast, but it has one sharp edge: anything the server prints to stdout corrupts the protocol. A stray print("starting up") in the server code can break every tool call. So stdio servers must log to stderr or to a file, never to stdout.

When a stdio server misbehaves, the logs are your lifeline. Send them to a file with timestamps, one line per event, including the tool name, the arguments received, and the result sent back. When a call fails, you want to open that log and see exactly what the agent asked for and what the server did about it, without replaying the whole session.

Example

Your custom MCP server keeps failing on get_order calls. You check its log file and see: 14:02:11 get_order args={"id": "ORD-881"} error: connection refused to db:5433. The agent was fine. The database was down. Without that one log line, you would have spent an hour suspecting the agent, the config, and the protocol. Log to stderr, log every call, save yourself.

Measuring what a tool server costs

Tools are not free. Every tool call adds tokens to the conversation: the tool description in the prompt, the arguments the agent writes, and the result that comes back. A tool that returns 50,000 rows will flood the context and drown out everything else. Measure three things: how often a tool is called, how many tokens its results consume, and whether the agent actually uses the results.

The cheapest fixes are the most effective. Paginate large results. Return summaries instead of full dumps. Trim verbose descriptions. If a tool gets called but its results never influence the answer, consider whether the description is misleading the agent into calling it. A tool the agent does not need is pure cost.

Example

Your list_tickets tool returns full ticket bodies and costs 8,000 tokens per call. You change it to return title, status, and assignee only, with a get_ticket_details tool for the full body. Calls drop to 400 tokens each. The agent still gets everything it needs, one detail call at a time, and your per-task cost falls by 90 percent.

Hardening a tool connection

A tool connection is a door into your systems. Treat it like one. Give each server only the credentials it needs, scoped as narrowly as possible: a read-only database user, a token that can read tickets but not delete them. Run servers with the least privilege the job allows. And assume the agent will eventually call a tool with surprising arguments, because it will. The server should validate inputs and reject anything dangerous, not trust the caller.

Three habits cover most of the risk. One: no destructive tools in the default connection. Add write tools only when a task needs them, then remove them. Two: timeouts on every call, so a hung server cannot freeze the agent forever. Three: keep server software updated, since MCP servers are network-facing code like any other.

Example

Your database MCP server connects with a read-only user and blocks any query containing DROP, DELETE, or ALTER. When a task genuinely needs a write, you temporarily enable a second config with a write user, run the migration with the agent watching, then disable it. The default state is safe. The dangerous state is deliberate and temporary.

Seeing what the agent sends

Trust, but verify. The agent decides on its own which tools to call and what arguments to pass. Most of the time it gets it right. The times it does not are instructive, and sometimes alarming. So make tool calls visible: turn on the agent's tool-call logging, or run a proxy that records every request and response. You want a record of what was called, with what arguments, and what came back.

Review this log after any important task, and skim it regularly. You will catch misread arguments, tools called when they were not needed, and the occasional genuinely surprising choice. This is also how you debug "the agent did something weird": the log shows you the exact moment things went sideways, which beats guessing every time.

Example

You review the log after an agent-run data cleanup and spot a delete_record call with {"id": "ALL"}. The agent misread your "clean up all the test records" as a bulk delete. The permission gate blocked it, but the log showed you the misinterpretation. You reworded your instruction to "delete records tagged test-fixture only," and the next run was clean. The log turned a near miss into a permanent fix.

Choosing a permission mode per task

Agents can run in different permission modes, and the right mode depends on the task, not your mood. A typical spread: read-only for exploration and research, ask-first for anything that changes files or calls external services, and auto only for tasks you have done a hundred times and could redo in your sleep. Match the mode to the blast radius.

Here is the habit that saves people: start every task one mode stricter than you think you need. Exploring a new repo? Read-only. Writing code in a familiar repo? Ask-first until the plan is solid, then relax it for the mechanical parts. Running your standard test suite? Auto is fine, it is reversible and fast. Tighten the mode when the stakes rise, loosen it when the work is boring and safe.

Example

You ask the agent to investigate a production bug. You start in read-only mode: it reads logs, code, and recent commits, and proposes a fix. You review the plan, switch to ask-first, and approve each change as it lands. The bug is fixed, nothing else was touched, and you never once wondered what the agent was doing behind your back.

Allowing the commands the task needs

Ask-first mode gets annoying fast if the agent asks permission for every ls and pytest. The fix is an allowlist: pre-approve the safe, predictable commands the task needs, and keep the gate for everything else. Most agents let you allow commands by pattern, like pytest * or git status. Build the allowlist from the task, not from habit: what does this specific job need to run?

Keep the allowlist tight. Allow pytest tests/, not bash *. Allow git diff and git log, not git push. The whole point is that the boring commands flow while the dangerous ones still stop for your eyes. Review your allowlist every few weeks. Permissions accrete like clutter, and a stale allowlist is barely better than no gate at all.

Example

For a bugfix task you allow: pytest *, ruff check *, git diff, git log *. The agent runs tests and linters freely, asking nothing. When it wants to run a database migration script, the gate fires and you get to say yes or no. You answered three prompts instead of thirty, and the one that mattered still reached you.

Where a setting comes from

When the agent behaves unexpectedly, the culprit is usually a setting you forgot you set. Agents layer their configuration: built-in defaults, then your personal config, then the project config, then environment variables, then command-line flags. Each layer overrides the one before it. Knowing this order turns "why is it doing that?" from a mystery into a checklist.

Debug it top-down. Check the command you ran for flags first, since flags win. Then environment variables, which are invisible and therefore the usual suspect. Then project config, then personal config. Nine times out of ten, it is an environment variable set months ago for a different task, still hanging around and still winning.

Example

The agent keeps using the expensive model even though your config says otherwise. You check flags: none. Environment variables: there it is, AGENT_MODEL=premium, set during a demo three months ago and forgotten. You unset it, and the config value takes effect again. Total debug time: two minutes, because you knew the layer order.

Writing a hook that blocks a mistake

Some mistakes you make once and never want to make again. Committing secrets. Pushing to main. Deleting the wrong directory. A hook is a small script that runs automatically at a defined moment, like before a tool call or after a file edit, and can approve, modify, or block the action. The blocking hook is the most valuable kind: it turns your one painful lesson into a permanent guardrail.

Keep hooks tiny and fast. A hook that takes ten seconds to run will be disabled within a week. Check one thing, decide pass or block, and explain the block in one clear sentence so the agent can fix the problem instead of just failing. Start with your most expensive past mistake. That is the hook worth writing first.

Example

You once pushed an API key to a public repo. Now a pre-commit hook scans staged files for anything matching sk-[a-zA-Z0-9]{20,} and blocks the commit with: "Possible secret in config.py line 12. Remove it or add the file to .gitignore." The agent reads the message, moves the key to an env var, and commits cleanly. The mistake can never happen again, because the hook never sleeps.

Keeping the project in charge

Here is a subtle failure mode: your personal config says one thing, the project needs another, and your personal preference quietly wins. Maybe you like a certain code style, but this project follows its own. Maybe your global instructions skip tests for speed, but this repo requires them. When personal and project settings conflict, the project should win. The project is the shared ground. Your preferences are the visitor.

Make this explicit in your personal config: "project instructions override these." And when you set up a project, say the same thing in reverse in the project's AGENTS.md: these rules apply here regardless of personal defaults. The few minutes this takes prevents the slow drift where every agent session subtly reshapes the project toward your habits instead of the team's.

Example

Your personal config says "keep functions under 20 lines." Your team's repo has no such rule, and its style favors slightly longer functions with fewer helpers. The project's AGENTS.md states: "Project conventions override personal preferences." The agent follows the project style, your teammate's review has nothing to flag, and your 20-line habit stays in your personal projects where it belongs.

Delegating to a subagent with narrower permissions

Sometimes a task needs help but not your full trust. Researching an unfamiliar codebase, trying a risky refactor, running untrusted scripts: these are jobs for a subagent with narrower permissions than yours. The subagent gets its own sandbox: read-only access here, no network there, no permission to touch production files. It does the dangerous or exploratory work, reports back, and you decide what to keep.

The pattern: you stay in control of the important decisions, the subagent handles the legwork inside its fence. Give it a tight brief: what to investigate, what it may touch, what it must never do, and what a good report looks like. When it returns, you get findings without exposure. If the subagent goes off the rails, the blast radius is the sandbox, not your project.

Example

You need to evaluate a third-party script before running it. You spawn a subagent with no network access and read-only repo access: "Read install.sh, summarize what it does, flag anything that touches the network, credentials, or files outside /tmp." It reports the script downloads a binary from an untrusted host. You never ran it. The subagent did the risky reading so you did not have to take the risky action.

Reading what the agent remembers

Agents keep notes about you and your work: preferences you stated, facts from past sessions, decisions you made together. This memory is powerful and occasionally wrong. Maybe it recorded a preference you stated once as a joke. Maybe it merged two similar facts into one incorrect one. If you never look at it, small errors compound into persistent misbehavior.

So read it. Most agents let you ask "what do you remember about me?" or expose a memory file you can open directly. Skim it every few weeks. Delete what is stale, correct what is wrong, and keep what is genuinely useful. Five minutes of pruning keeps the memory a helpful colleague instead of a gossiping one.

Example

You ask the agent what it remembers and find: "User prefers all code in TypeScript." You said that about one frontend project six months ago. Now it is nudging every Python script toward TypeScript. You correct it to: "Prefers TypeScript for frontend projects; Python for data work." The misbehavior stops that same day. The memory was never malicious, just overgeneralized. Reading it caught the drift.

Notes that go stale

Memory has a shelf life. "Deploy on Fridays" was true until the team moved to continuous deployment. "Use the old API client" was true until the migration finished. Stale notes are worse than no notes, because the agent acts on them with confidence. A confident wrong instruction beats a hesitant right guess for causing damage.

Fight staleness with dates and reviews. When you add a memory or a project note, include when it was true and what would make it false: "As of March, we deploy via the old pipeline; revisit after the migration." Then review on a schedule. Monthly is fine for most things. When a project changes direction, updating the notes is part of the change, not an afterthought.

Example

Your project notes say "run the full test suite, it takes 4 minutes." After a refactor, the suite takes 25 minutes, and the agent dutifully runs it for every tiny change, burning your afternoon. You update the note: "Run pytest tests/unit (30s) for small changes; full suite only before merge." One stale sentence was costing twenty minutes per task. The dated note would have flagged itself for review.

Directing the summary before compaction

Long sessions hit a context limit, and the agent compresses the conversation into a summary to keep going. This is called compaction, and the default summary is generic: it keeps what seems important to the model, which is not always what is important to you. The fix is simple: before a long session ends or compacts, tell the agent what to preserve.

A good direction is short and specific: "When you summarize, keep: the three design decisions we made and why, the two open questions, and the exact command that reproduced the bug. Drop: the dependency installation chatter and the dead-end approach." You are writing the table of contents for your own future session. Thirty seconds now saves thirty minutes of re-discovery later.

Example

After a four-hour debugging session, you tell the agent: "Summarize preserving the root cause (race in cache invalidation), the fix branch name, and the failing test name. Drop the environment setup steps." Next session starts with exactly that context. The agent picks up where you left off instead of re-reading the whole saga and re-learning the root cause from scratch.

Handing work to the next session

Sessions end. Work does not. The handoff habit is what separates people who lose an hour every morning from people who start instantly: at the end of a session, create a short handoff note. Where the work stands, what is done, what is next, and anything the next session must know. Store it somewhere the next session will actually see it: the project notes, a handoff file, or the agent's memory.

Keep the format ruthlessly consistent: Status (one line), Done (bullets), Next (bullets, ordered), Watch out (gotchas). If the next session is you tomorrow morning, this note is a gift to future you. If it is a teammate or another agent, it is the difference between continuity and starting over.

Example

Your handoff note reads: "Status: checkout flow refactor, 70 percent done. Done: cart page, payment form. Next: 1) wire up the order confirmation email, 2) run the full checkout test suite. Watch out: the email template uses the old branding variables, update them." Tomorrow you open the session, read four lines, and you are productive in two minutes instead of spending twenty reconstructing the state.

Turning repeated work into something the agent keeps

This is the whole page in one lesson: when you catch yourself explaining the same thing to the agent for the third time, stop explaining and start saving. The third time is the signal. The first time is a conversation. The second time is a coincidence. The third time is a missing skill, a missing instruction, or a missing note.

The conversion is mechanical. Notice the repetition. Write down what you keep saying. Decide where it belongs: one-liner goes in AGENTS.md, multi-step process becomes a skill, personal preference goes in memory, a guardrail becomes a hook. Then test it once from a fresh session. Congratulations: you just turned toil into infrastructure, and every future session inherits the improvement for free.

Example

Three times this month you told the agent: "When you finish a feature, update the changelog, bump the version in pyproject.toml, and draft release notes." The fourth time, you write the release-prep skill instead of typing the instructions again. From then on, "prep the release" does all three steps correctly. The repetition is gone, and the knowledge outlives any single session.

Tip

Keep a running "third time" list: a scratch note where you jot down anything you have explained twice. Review it weekly. Each entry is a future skill, instruction, or hook waiting to be written. This one habit compounds faster than any single customization.
